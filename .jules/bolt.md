## 2025-08-05 - Optimize Matching Data Allocation
**Learning:** In highly nested match calculations for arrays (like comparing profiles to projects or users to candidates), `Array.prototype.filter` creates intermediate arrays solely for measuring common intersection length, causing high GC overhead. Additionally, using nested `map()` and Set initialization during project looping causes O(N) intermediate allocations and lookups inside loops rather than amortizing costs with Sets beforehand.
**Action:** Replace filtering logic with O(n) accumulator loop patterns when only lengths or conditions are needed. Always evaluate when inner array modifications/typecasting (e.g., lowercasing) can be lifted out of iteration logic to occur once per matching session rather than on every matched item.
